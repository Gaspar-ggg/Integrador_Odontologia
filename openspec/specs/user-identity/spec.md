# user-identity Specification

## Purpose
Define el modelo persistente de identidades de usuario, roles de acceso, auditoría con soporte de baja lógica (soft delete), respuestas de error estandarizadas y la carga inicial de cuentas base.

## Requirements

### Requirement: User entity and roles persistence
The system SHALL persist user accounts with unique username, unique email, password hash, role (`ADMIN`, `RECEPCION`, `ODONTOLOGO`, `PACIENTE`), and active status.

#### Scenario: Create new user account
- **WHEN** a valid user entity is saved to the repository
- **THEN** it is persisted with an autogenerated ID, creation timestamp, and active status true

#### Scenario: Reject duplicate username or email
- **WHEN** a user is saved with an existing username or email
- **THEN** the system rejects the persistence operation with a unique constraint violation

### Requirement: Auditable entity base and soft delete
The system SHALL provide common auditing timestamps and soft delete behavior for domain entities.

#### Scenario: Soft delete deactivation
- **WHEN** a user account is deactivated via soft delete
- **THEN** its active status is updated to false and repository active queries exclude the record

### Requirement: Standardized global error response
The system SHALL intercept unhandled exceptions and validation errors returning a consistent JSON error payload matching `ErrorResponseDTO`.

#### Scenario: Resource not found response structure
- **WHEN** a requested entity is not found by identifier
- **THEN** the system returns HTTP status 404 with a JSON payload containing timestamp, status 404, error name, message, and path

#### Scenario: Validation constraint violation response structure
- **WHEN** an incoming request payload fails bean validation constraints
- **THEN** the system returns HTTP status 400 with validation details and uniform JSON structure

### Requirement: Initial default accounts seeding
The system SHALL automatically seed default administrative accounts upon application startup if they do not exist.

#### Scenario: Seed execution on application startup
- **WHEN** the application starts up and no admin user exists in the database
- **THEN** the system creates default admin and reception accounts with secure BCrypt password hashes
